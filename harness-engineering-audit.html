DeepSeek Harness 工程优化审计

结论不是“重写核心”。当前架构的能力拆分与持久化约束总体成熟，真正值得优先处理的是工程控制面的重复扫描、生成目录的体积与变更噪声、热点 UI 文件的责任密度，以及少数已失去消费者的兼容表面。

建议策略：先减维护成本，再测运行时收益 基于架构文档、全仓静态清点、依赖中心度、热点文件、近期变更频率、现有 Agent Note 与性能基准决策。未把文件大小直接等同为性能问题。

执行结论

优化重点应落在“高频改动 × 高责任密度 × 可验证成本”交集，而不是按包数量做机械合并。

总体判断

Harness 的核心约束相互一致：插件通过能力接口组合，模型可见输入可由 Session 日志重建，Host/Client 编译面显式分离，发布过的 Session 代际不可覆盖。这些约束解释了相当一部分代码量，不能当作普通重复代码处理。

工程上的主要机会集中在外围：多个静态 gate 分别构建完整 TypeScript Program；Host/Client 的生成式 Cordis 目录经首轮压缩后仍有 709.3 KB；几个高频 UI 文件同时承担数据建模、状态、交互和渲染；测试按文件并行，但存在 2,000–6,000 行的单文件长尾。

阶段一已落地已删除 workspace 死参数和过渡期迁移脚本；测试拆分完成，但 isolated 墙钟没有获得性能收益。
先测再改共享静态分析索引、压缩生成目录、自动 affected-check 选择，都需要基线和负向对照。
不建议触碰双 LLM 适配器、Session persistence 能力接口、发布代际和 wire/durable 校验不是“冗余”。

Harness 结构与优化落点

端到端链路越靠左，越接近可替换的能力定义；越靠右，越接近持久化与用户投影。优化必须保留中间的事件记录与生命周期语义。

Profile / CordisLoader 组合插件、配置与作用域。固定成本来自包发现、解析和构建。
能力接口Service Definition / Provider / Consumer。小包常是刻意保持的替换点。
Agent looppre-step、request、tools、stream、stop 等事件驱动一个回合。
Session log模型可见输入的权威记录；迁移、发布、恢复承担兼容义务。
Host / Client投影、RPC、会话历史与 Web UI。当前最大的源码与交互复杂度集中区。

优化落点：构建/校验共享索引位于装配之前；目录压缩位于能力描述投影；UI 拆分位于 Client 消费端；Session 主链保持行为不变。

明确不做的优化

这些限制来自已发布数据、能力替换和生命周期正确性，不是保守偏好。

不因“包小”合并能力接口`browser-use`、`computer-use` 等小包承担独立 Service Definition；只有消费者与演进节奏证据才能推翻拆分。
不折叠双适配器为一个条件分支LLM/provider twins 默认视为有意设计；共享代码只有在真正删除所有权和测试成本时才成立。
不跳过 durable / wire 校验换速度Session 代际、配置、进程、网络和持久文件仍是必须验证的输入边界。
不改写已提交的 Session 代际迁移只能发布相邻的新版本 successor，旧代不可移动、覆盖或删除。
